=============================
DW99 内核移植与启动排障记录
=============================

项目与对照基线
==============

DW99 使用展锐 SL8541E（SharkLE）平台。本仓库的 7.3 分支以
``upgrade-linux-7.3`` 为工作分支。厂商行为以 Watch-GKI 4.4.147
的 DW99 配置、设备树和驱动为对照，审查时的提交为 ``4d3de52cc``。
用户态兼容以现有 HyperOS 调试版的 ``vendor.img`` 为对照，其中的
厂商模块原先面向 Linux 4.14.133。

DSH 阶段
========

1. 将 DW99 主线测试树更新至 Linux 7.3.4，保留原有板级驱动和设备树，
   处理内核升级产生的接口冲突并恢复 ARM64 编译，同期将 ReSukiSU
   迁移到 BakaSU，并同步 SuSFS 2.4.0。相关基线见 ``d4de4ef72``、
   ``40fe4644c`` 和 ``5195dbf4f``。
2. 根据多轮早期启动日志，修复 PTM 通道名在读取通道数量之前分配、
   SharkLE 深睡眠 regmap 错误处理等问题（``93c55958c``、
   ``ffe6e2c98``）。随后将启动控制台收敛到 USB，保留 U-Boot
   早期端点的 ``musbec``，配置 ``keep_bootcon console=ttynull``
   （``a3d5ca639``）。
3. 修复 WLAN 提前调用 WCN 所致的空指针，通过探测延迟等待 WCN 和
   硬件锁就绪（``7b04b003e``）。调整 ADI 父设备运行时电源管理
   （``d9d66fc37``）。随后修复 SC2721 电源供应和 FGU 注册失败后的
   错误处理（``07ddc1caf``）。后续归档日志已显示 FGU 成功完成探测。
4. 对照本地原厂启动链找到 SC2721 PMIC 看门狗复位方式，将其接入
   DW99 的正常重启和 panic 复位路径，并提前注册到 FGU 探测之前
   （``1a94876fe``、``32863d444``）。DSH 已构建并打包 PMIC 复位
   镜像，远端构建通过。实机复位行为仍需验证。
5. 多次启动采集仍出现随机截断。可核对的一次归档使用
   ``32863d444``，约在启动后 0.339571 秒截在 DSI 初始化消息中途。
   DSH 已开始排查 USB PHY 接管及 ramoops、PWM、mailbox 警告。
   后续调用遇到请求配额和授权错误，停在源码分析阶段。

Codex 接续
==========

重新定位整理后的 Windows 端工具和 WSL 工作树，核对实际构建配置，
继续使用同一 7.3.4 基线。本地诊断工作修复 PWM 驱动重名和
``pwm_chip`` 注册问题，把 ramoops 改成 7.3 能识别且按 4 KiB 对齐的
预留内存节点，并为 DW99 的两条 mailbox SPI 显式声明当前 GIC 初始化
采用的电平触发。ramoops 保留原厂预留范围，并为控制台配置 128 KiB。
同布局内核可以在保持该段 RAM 的重启后读取记录。

正常诊断镜像保留 MUSB 与 USB PHY，记录 PHY 供电、探测断电和控制器
复位。对照镜像仅在生成的 DTB 中禁用 MUSB 和 PHY 两个节点，两份
镜像内的 ARM64 内核及 ramdisk 完全相同。编译、DTB 比对和 SPRD
封装逐段校验均已完成。对照镜像用于区分驱动接管与其他日志中断原因，
其正常 USB gadget 功能随节点一起关闭。USB 早期控制台直接写引导器
遗留的 EP5，Watch-GKI 的常规 PHY 探测会主动断电及隔离，构成一个
明确的待测断点。现有记录仍不足以确认每一次日志截断的原因。

Windows 采集器改为有限超时读取，记录端口静默、消失和重连，同时独立
保存原始字节和事件流。现有 FDL 批处理在原命令成功退出后启动采集器，
使用自动识别的 SPRD 端口。成功、FDL 失败及采集失败均经过命令模拟，
设备端采集仍待验证。

Watch-GKI 驱动审查
==================

两份 DW99 DTB 各保留 315 个自身及祖先均启用的 compatible 节点。
逐项核对了匹配表、生成配置、链接符号和 ROM 用户态接口，确认以下
影响启动或兼容的差异。

* USB UDC 移植丢失厂商 charger 初始化、状态通知和退出调用，
  MUSB glue 仍直接使用 charger 指针。
* SC2721 的 ``INT_EN`` 在新版 regmap IRQ 接口下被当作普通
  mask 寄存器。ADC 的 IIO 回调和底层函数重复获取同一把 mutex，
  板温读取可以在启动中触发。ADC 及 PMIC eFuse 还有硬件锁语义差异。
* SIPC 从旧四参数 ``vm_map_ram`` 切换到新版三参数接口时，
  丢失了本应给 SWCNBLK 共享控制环使用的非缓存页保护属性。
* ADF 和 JPEG 的 32 位 ioctl 分派被替换为返回 ``-ENOTTY`` 的
  占位实现。部分相机、VSP 和 ION 的兼容入口也缺少有效缓冲区。
  ROM 里确实存在使用这些接口的 32 位厂商库。
* 现有构建的厂商 GPU、蓝牙和 FM 模块尚未交付。ROM 的原模块和
  7.3 具有不同的内核符号版本，WLAN 则已有内建实现。

兼容路径与验证状态
==================

* Mali。ROM 的内核模块和 Watch-GKI 源码均为
  ``r28p0-01rel0``、UK ABI ``11.13``。保留 ``/dev/mali*`` 及
  现有 ioctl 是复用 HyperOS EGL/GLES 库的目标。Watch-GKI 已有
  SharkLE 电源管理和调频实现。移植时需核对 dma-buf、内存映射、
  页固定、shrinkers 和 32 位 ioctl，再进行实机渲染验证。
* 蓝牙和 FM。使用 Watch-GKI 的 SIPC 源码，保留 ``sprdbt_tty.ko``、
  ``sprd_fm.ko``、``/dev/ttyBT0``、``/dev/fm`` 和 FM 的 32 位
  ioctl。现有 Android init 已按这些模块名加载。优先修复共享控制
  环的映射属性及固件读取逻辑，然后基于同一 7.3 构建的符号版本
  生成模块。实际 WCN 启动、蓝牙和 FM 功能仍需板上验证。
* 构建验证的范围包括 ARM64 内核链接、DTB、诊断镜像封装及 Windows
  采集器离线流程。兼容驱动移植已开始，后续以目标内核的模块构建和
  ABI 校验结果更新本记录。

第一轮厂商兼容移植
==================

* 将 SIPC 控制环映射恢复到 Watch-GKI 使用的非缓存页属性，并同步
  notifier 解绑与正在执行的回调。WCN 分区读取按实际读入字节推进，
  固件载入前核对目的区域长度，失败时向上层返回错误。
* 蓝牙和 FM 保持原 ROM 的模块名及设备节点。FM 保留 32 位 ioctl
  结构，蓝牙和 FM 分别绑定各自的设备树节点。SC2721 的 IRQ 极性、
  ADC 的重复加锁和 PMIC eFuse 的硬件锁也已适配。
* 从 Watch-GKI 引入 SharkLE Mali kbase r28p0，保留 UK 11.13
  用户态头文件。GPU 的设备树散热绑定接入 7.3 devfreq 和 Energy
  Model。散热功耗模型保留厂商系数，漏电估计采用板级临界温度作为
  上界，实际限频仍由 DT 温区的温度和阈值决定，需在板上复核。
* 恢复 USB gadget 充电器的初始化、连接和断开通知以及解绑清理，
  修正 MUSB 的充电器引用和退出顺序。已分别编译检查启用和禁用
  充电器的配置。
* HyperOS 目前使用厂商 Vulkan 1.0 与 GLES 混合渲染。此次工作保留
  现有用户态驱动的 ABI。更高的 Vulkan 版本需要经过适配和验证的
  用户态 GPU 驱动，移植内核模块本身不会增加 Vulkan 功能。


2026-11-20 实机采集复核
=======================

* 原 USB 诊断镜像在内核时间 0.162559 秒、USB 核心注册后失去
  主机串口；厂商模块构建 ``51ab1f3ec`` 在 0.173211 秒的 Trusty
  版本行后也失去串口。Windows 两次均收到 ReadFile 995，采集记录
  报告设备自行断开。该对照没有记录重启或 panic。
* 同一轮旧 USB 诊断内核关闭 ``usb@20200000`` 与
  ``hsphy@20e00000`` 后，继续通过 PMIC 看门狗、FGU 和 DSI 探测。
  日志还越过 WLAN 的 WCN 启动失败，最后停在 0.435709 秒的
  CST9217 探测入口。该轮端口仍在，采集由操作者结束。三份日志
  均未记录 ``/init``。早期控制台直接使用引导器 EP5，端口是否
  枚举、能否继续收字节以及内核是否仍运行需要分别判断。
* 采集使用已在板上工作的原版 ``publish/usb_log_reader.py``。
  它清 RTS、置 DTR，以单字节阻塞方式读端口。此前的替换版能
  枚举 COM5，但一次实机采集在初始化阶段失败，原始文件为零字节。
  当时的错误处理把 Win32 失败码误报为 0，无法从该记录确定
  失败的具体调用。
* 以 ``51ab1f3ec`` 制作三份隔离镜像，沿用同一内核与 ramdisk。
  第一份关闭 MUSB 与 PHY，第二份在同条件下额外关闭
  ``hynitron@5a``，第三份仅关闭 MUSB 并留 PHY 探测。PHY
  探测自身会断电及隔离，独立启用能测试它是否足以中止 EP5。
  若端口仍在且没有后续日志，保留至少 250 秒的完整采集，以等待
  当前 120 秒采样周期的 hung-task 栈。
* CST9217 探测入口后的电源、复位、首笔 I2C 目前都是候选。
  R8P0 I2C 驱动原先无限等待完成中断。现在每条消息等待最多一秒，
  超时记录地址和控制器状态，同步 IRQ 线程后重新初始化控制器。
  同时增加触控探测的动态调试点。目标是避免一次丢中断无限阻塞
  PID 1，并指出实际停在哪一步。总线超时及启动结果仍待板上验证。


2026-11-20 第二轮实机对照
=========================

* 三张对照使用同一内核 ``51ab1f3ec`` 与 ramdisk。仅启用 USB PHY
  时，于 0.225494 秒的记录后收到 ReadFile 995，端口随后消失。
  MUSB 与 PHY 均禁用时，端口保留，最后记录为 0.436281 秒的
  CST9217 探测入口。PHY 单独启用即能复现早期 USB 掉口，此轮
  未记录确切的 PHY 寄存器写入或重启。
* I2C 超时版 ``167d9dba3`` 停在 0.439374 秒的
  ``enabling vddsdcore``。其后还要从 ``regulator_enable()`` 返回，
  再执行 20 ms 的稳定等待，两者之间当时没有标记。日志未到
  GPIO 复位或首笔 I2C，因此这个停点发生在触摸 I2C 之前。
* 在相同 USB 禁用配置上只关闭触摸，启动越过该点，进入
  20600000.sdio eMMC 初始化。9.452090 秒 AP 看门狗超时，
  阻塞栈显示 PID 1 在 ``mmc_power_up()`` 的第一处
  ``usleep_range_state()`` 等待。9.459972 秒 panic，
  后续记录了准备重启，未观察到实际重启或下一次启动。
* 设备树的 Arm 定时器原先只列 PPI 14、10，未标名称。7.3 在
  Cortex-A53 的此启动路径选择 EL1 非安全物理定时器，却按位置
  把第二条 PPI 10 当作 EL1 物理中断。PPI 10 属于 EL2 物理
  定时器，EL1 物理应使用 PPI 14。这解释了为何计数器时间仍
  在推进而定时睡眠没有及时唤醒。已用同一内核镜像封装仅修正
  定时器中断映射的 DTB 对照，另有仅追加 ``cpuidle.off=1`` 的
  对照。首选中断映射对照。两份均保留触控，禁用 MUSB 和 PHY。
* Watch-GKI 另有 ``sprd,bcevt-r4p0`` 32.768 kHz 广播时钟事件驱动。
  7.3 以前只保留对应设备树节点。深度 idle 声明本地定时器停止，
  所以应恢复独立广播定时器，同时保留本地定时器。CPUFreq 在
  相同日志中还出现频率表初始化失败和 ``cpufreq-clus0`` 引用
  计数警告。驱动把频率表留在局部变量后校验空的 policy 表，
  多条路径又释放了同一个设备树引用。两个问题均已修复。

复现构建
========

在 DW99 源码树根目录运行。三个模块必须和一同使用的内核来自同一次
构建。脚本会核对每个模块的 vermagic，CI 将内核、设备树、符号版本
表和三个模块保存在同一构建产物中。

.. code-block:: sh

    make O=out-dw99 ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
         lineageos_dw99_72_defconfig
    make O=out-dw99 ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
         -j"$(nproc)" Image sprd/dw99.dtb modules
    tools/build-dw99-vendor-modules.sh out-dw99 out-dw99/vendor-modules

在 WSL 中，三个 ARM64 模块均通过目标内核符号表的严格
modpost 校验。Mali 继续使用 Watch-GKI 的 UK 11.13 和 ioctl
ABI，设备树仍使用板级的 GPU 和 SIPC 绑定。

实际开机、GPU 渲染、蓝牙和 FM 仍需板上验证。32 位 ADF、JPEG、
相机和 ION 的其他兼容问题仍按审查记录跟踪。
